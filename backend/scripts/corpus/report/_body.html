Readiness is not 87%. The previous revision scored architecture, tests and code structure — all of which were real. None of it was evidence that the product answered a buyer. The first time 321 live queries were run through the chat, 13.1% produced a usable answer. Everything below is what that measurement found and what it cost to fix.

The measurement was wrong first

Before any finding can be trusted, the instrument has to be. Mine was broken, and so were the two eval scripts already in the repo.

Every test query arrived at the server empty Instrument
The chat route reads the question from action.payload.text; BodySchema keeps text/query/label and discards everything else, including a top-level message. My runner sent payload.message. So the server received "" on all 321 queries — which is why extractIntent returned {}, intentState was COLD, and every answer was a greeting. The first "13.1% baseline" measured the product's reply to an empty string. live-chat-test-eval.ts and run-stress-test-suite.ts had the identical bug, so every result they have ever produced measured the same thing. All three fixed.
An empty message bought a full paid LLM turn Cost
The schema accepted it, the router ran intent extraction on "", and the chain spent a real Gemini call to produce a greeting. Three separate callers in this repo hit that path. Now a 400.

What was actually broken

In order of what they cost. Four of the six were invisible in logs and in the cost table — they read as normal operation.

The paid Gemini key was answering nothing at all Trust
Explicit context caching attached a cachedContent to a request that also set system_instruction and tools. Gemini rejects that combination outright — 400 CachedContent can not be used with GenerateContent request setting system_instruction, tools or tool_config. Our prompt always sets both, so every cache-attached request 400'd and rolled onto GEMINI_API_KEY1, a free-tier key that cannot hold a cache at all (limit=0) and 429s on quota. The billed account served none of the traffic it was paying for. The only symptom was a ROLLOVER line with no reason attached.
Every tool call failed on Gemini 3.x Trust
400 Function call is missing a thought_signature in functionCall parts. We rebuilt the model's functionCall part from name and args, discarding the thoughtSignature Gemini attaches to it. Every tool-backed lookup — EMI, stamp duty, floor plans, cost sheets, RERA — therefore 400'd and fell through to a tool-less provider that answered from memory instead. Fixed by echoing the model's own part back.
Answers stopped mid-sentence and read as complete Trust
maxOutputTokens budgets thinking and text together, and gemini-3.x thinks by default. On a hard question the model spent almost the whole 1,500 on thoughts and stopped ~15 tokens into the reply: "Historically, Noida Sector 23, Sector 34, and". Thirteen of 67 demo answers ended that way, each reported by the API as a normal completion. Now a capped thinkingBudget added on top of the reply allowance — and thoughtsTokenCount, which bills at the output rate, is finally counted.
A stub tool handler made the model loop and return nothing Dead end
Five call sites paired a full tool catalogue with onToolCall: async () => ({}). The model called a tool, received an empty object, called again, exhausted every cycle and emitted no text — a blank reply and a full bill for the thinking behind it. Comparison queries were the worst hit: the four-sector question returned "" after generating 453 tokens. Comparison went 4/8 → 8/8.
Weak providers parroted a canned string as their answer Trust
The HONEYPOT RULE ordered an exact reply for prompt-extraction attempts. Mistral and Cerebras latched onto it as the most salient literal in a 5.7k-token prompt and emitted it for ordinary queries — 186 of 321 came back as "I am RealtyPal… How can I help you with your property search today?". Prompt extraction was already blocked deterministically by inputGuardrail before the model, so the rule was redundant as well as harmful. Replaced with a behavioural instruction carrying no literal, plus a test that fails if any canned reply returns to the prompt.
Failover fired on healthy requests Latency
An 8-second first-token deadline, chosen for "fast rollover", fired 18 times per 67-query run on requests that were merely thinking. Every one landed on the free-tier key. Now 25s — rolling over early only helps when the next leg is healthier, and it was not.

Corrections to the previous revision

Two of its headline claims were wrong, and one of mine from this session was wrong by a factor of twenty.

"Enable billing → explicit caching → ~60% input cost" was backwards
Billing was enabled. Explicit caching then broke the paid key on every single turn, and it caches less than the free implicit cache does. The previous revision's limit=0 reading was correct but the conclusion drawn from it was not: implicit caching had never hit because the measurement was taken on a free-tier key. On the billed account implicit caching reports 78.2% of prompt tokens served from cache (8,095 of 10,346) with no request changes at all — more than the 6,196-token head explicit caching could store. Explicit caching is now off by default and guarded so it cannot silently return.
I reported $0.53 of spend. The real figure was roughly twenty times that.
Ten Gemini call sites — intent extraction, chip generation, extended intent, history compression, session summaries, ghost-pool classification, buyer narrative, document parsing — never wrote an AiUsageEvent. Several run on every turn. Mistral and Cerebras recorded nothing either: neither set stream_options.include_usage, so 238 of 321 queries were served at a recorded cost of exactly zero. Cerebras's model id had no price row and billed $0 with real token counts. A day of measurement drained a ₹1,000 prepaid balance while the dashboard read fifty-three cents.
A "13.1% baseline" that measured nothing
Reported before I checked what the server received. The number was real; what produced it was an empty string, not the product. Superseded by the 69.8% run on a corrected harness.
I wrote that we hold no rental data. We do.
While tightening the scope rule I told the model to deny all rent figures. SectorIntelligence.avg_rent_3bhk_monthly exists, and rental yield is an in-scope investment question in the corpus itself. Rewritten to permit a rent figure visible in an injected block and forbid a composed one.

Spending cannot run away again

The under-reporting was the smaller half. Nothing anywhere stopped spending.

The only budget guard in the system was isOverDailyBudget, which covers signed-in users on the chat route. A batch script running as a guest crossed no limit at all, and neither did any of the ten background call sites. Three things changed:

One metered client, no direct constructionCost
Every non-streaming Gemini call now goes through meteredClient(), which checks the budget before the call and writes an AiUsageEvent after it. new GoogleGenAI appears in exactly one place now. Mistral and Cerebras request usage in the stream and record it.
A hard daily ceiling across every callerCost
GEMINI_DAILY_BUDGET_USD, default $2. Exceeding it throws, which the fallback chain already handles as an ordinary provider failure — so a blown budget degrades to Mistral rather than to an error page. A failed spend read reports the budget as exhausted, never as zero: the gate fails closed.
An unpriced model says soCost
A model with no price row silently billed $0 forever and looked like free traffic in every dashboard. It now warns once per model, so a provider renaming a model cannot quietly turn its traffic free.

What the corpus taught the prompt

The 321 queries were folded into 255 distinct shapes. The most useful thing in them was not any single question — it was the shape distribution, which contradicted what the prompt assumed.

Every clause is a constraint, including the conflicting ones

Nearly two thirds of real queries have no verb and no question mark. The prompt was written for conversation and treated these as under-specified, which is why the commonest reply to "2 bhk in noida" was a request to rephrase. The rule now is that a bare phrase is the fullest question it could reasonably be, answered as such — assume, state the assumption, move on. A clarifying question is earned only after an answer, never instead of one.

This is generalisation from the corpus, not memorisation of it. Nothing in the prompt names a query, a sector or a builder from the files: the six shapes and the two rules under them apply to questions nobody has asked yet. There is no fine-tuning here and there should not be — the failures measured were routing, budgeting and API-contract defects, none of which a trained model would have fixed.

Out of scope, handled gracefully

Roughly 12% of real Noida search demand is for things V1 does not sell — rentals, resale, plots, commercial, auction stock. A flat refusal loses the buyer; a fabricated figure loses their trust.

The failure here was specific: asked for average 2 BHK rent, the assistant answered "₹15,000 to ₹40,000 per month" — confident, precise, and ours by implication. It arrived from a second route entirely, groundedAnswer.ts, which does live web search with its own prompt that the scope rules never reached.

Both routes now carry the same directive, injected only on the turns that need it and detected by regex on the incoming message — so the instruction is in place before the first token. A guardrail that inspects the finished answer cannot help: by the time it sees the figure, the figure has been streamed. The instruction is not "refuse". It is: give the web-sourced range, attribute it in the same sentence, mark it as indicative rather than verified, answer any public law or process question directly, then bridge once to the purchase question behind it — and if there is no honest bridge, stop rather than steer toward listings.

The exception that had to be carved out. Rent is not uniformly absent: SectorIntelligence holds avg_rent_3bhk_monthly, and rental yield is a live investment question. A blanket "we have no rent data" would have forced the model to deny data we hold. The rule is a figure you can see in a block, never one you compose.

Not fixed, and why

Latency is 3× the stated targetOpen
p50 10.4s against the <3s in CLAUDE.md. Intent extraction was the cheapest third and is now skipped for short queries; the rest is the model's own thinking time on a 5.6k-token prompt. Getting under 3s means a smaller prompt or a smaller model for the common case, and both trade against the quality just bought.
Mid-stream stall still truncatesOpen
Once a token is sent, SSE cannot retract it, so a stall can only be truncated with a notice. The failover window was ~50 characters or the first newline — and every answer opens with a markdown heading, so the window was effectively nil. Now 250 characters, length-only. It fired zero times in 400 turns, so this is a widened safety margin rather than a verified fix.
Grading is mechanicalOpen
The harness catches deflections, empties, truncation and undeclined out-of-scope answers. It cannot tell a well-reasoned recommendation from a plausible one. Several "failures" in the last run were good answers marked down for ending on a question. A judge pass is the next honest step, and it costs real tokens.
Four env vars are undocumentedOpen
.env.example is outside my write permissions. GEMINI_DAILY_BUDGET_USD, GEMINI_THINKING_BUDGET, STREAM_BUFFER_CHARS and INTENT_FAST_PATH all default correctly in code, so nothing breaks — but the next person will not know the ceiling exists until it stops them.
